    Velux Roof Windows with KNX Buttons, through Home Assistant and the KLF 200

    On this page

    • Before you buy: the KLF 200 is discontinued
    • How the bridge works
    • The example
    • Airing with guards
    • On the phone

    Our roof windows and their outside screens are Velux INTEGRA products. They speak io-homecontrol, a radio protocol, not KNX. The rest of the house is KNX, and the wall buttons and the visualization were planned to move the Velux windows like any other blind. Something has to translate between the two.

    In our house that is Home Assistant: it receives the KNX telegrams, moves the Velux products through a Velux KLF 200 gateway (bought in 2023), and sends their positions back to KNX. This page shows that bridge with a small, made-up example you can adapt, and what the end of the KLF 200 means for new installations.

    Before you buy: the KLF 200 is discontinued

    Velux has replaced the KLF 200 with the KLF 150. That is not a drop-in replacement for Home Assistant:

    • The Home Assistant Velux integration talks to the KLF 200 over the local network. Its documentation says the KLF 150 is not supported, “even though Velux markets it as the replacement for the now-discontinued KLF 200”, because the KLF 150 has no local API.
    • Velux describes the KLF 150 as an interface for switches and sensors with potential-free contacts: it can control 5 products or 5 groups. As far as I can tell from that description, KNX binary outputs could drive it like a set of buttons, but Home Assistant would then know nothing about positions. So: if you already have a KLF 200, everything below works, and you may still find used units.

    For a new installation, the route that works with Home Assistant is the VELUX ACTIVE gateway (KIG 300). Home Assistant’s Velux documentation says to integrate it with the HomeKit Device integration, which talks to the gateway locally, without a cloud. Its windows and screens then appear as cover entities, and the bridge below should work the same way with those entities in place of the KLF 200’s. I haven’t run that combination myself.

    Two other routes, for completeness:

    • Somfy TaHoma: Somfy’s compatibility list 2025 v1 (page 12) lists Velux io roof windows, roller shutters (SSL/SML io) and screens (MML) for the TaHoma switch and TaHoma Rail-DIN S. Home Assistant’s Overkiz integration can talk to the TaHoma switch locally. Check your exact products against the list.
    • Directly from KNX: OpenKNX OFM-IOHomeControl is community firmware for an ESP32 with an 868 MHz radio that speaks io-homecontrol on one side and KNX on the other, without a manufacturer gateway. It is in active development, and the project says most device types are still untested.

    How the bridge works

    KNX button or visualization
  → group address (move, stop, position)
  → Home Assistant automation (knx.telegram trigger)
  → one script per Velux product
  → Velux cover entity → KLF 200 → io-homecontrol → window or screen

Velux position changes
  → Home Assistant automation (state trigger)
  → knx.send to the position status address → button LEDs and visualization

    Three design choices made it reliable:

    1. One script per Velux product, in restart mode. A new command for the same window replaces the one still running; other windows are not affected. The dispatching automation only starts the script and doesn’t wait, so a slow gateway never holds up the next telegram.
    2. Positions are converted once, in both directions. A KNX blind position (DPT 5.001) counts 0 % as fully up or open; a Home Assistant cover counts 100 as fully open. Commands from KNX become 100 − value, and the status back to KNX does the same.
    3. No position, no status. When the gateway restarts or an entity is unavailable, the cover has no position. An early version of my bridge turned that missing value into 0 with a default, and then into 100 % for KNX: the visualization would show a closed window, whatever its real position. Only a real position from 0 to 100 goes to the bus.

    The example

    The example drives one roof window and its screen. All names and addresses are made up:

    Function Window Screen Data point type
    Move (up/down) 24/0/1 24/0/2 1.008
    Stop 24/1/1 24/1/2 1.007
    Position 24/2/1 24/2/2 5.001
    Position status 24/3/1 24/3/2 5.001

    cover.roof_window and cover.roof_window_screen are the entities of the Velux integration, and binary_sensor.rain is a rain sensor, for example from a KNX weather station. The type on each trigger tells Home Assistant how to decode the value, so it works without importing the ETS project.

    Put it into a package, for example packages/velux_knx.yaml:

    # Velux window and screen, driven from KNX through Home Assistant (made-up addresses).
script:
  velux_window:
    alias: "Velux window: one command at a time"
    mode: restart
    sequence: &velux_command
      - choose:
          - conditions: "{{ command == 'stop' }}"
            sequence:
              - action: cover.stop_cover
                target: { entity_id: "{{ cover }}" }
          - conditions: "{{ command == 'open' }}"
            sequence:
              - action: cover.open_cover
                target: { entity_id: "{{ cover }}" }
          - conditions: "{{ command == 'close' }}"
            sequence:
              - action: cover.close_cover
                target: { entity_id: "{{ cover }}" }
          - conditions: "{{ command == 'position' }}"
            sequence:
              - action: cover.set_cover_position
                target: { entity_id: "{{ cover }}" }
                data: { position: "{{ position }}" }
  velux_screen:
    alias: "Velux screen: one command at a time"
    mode: restart
    sequence: *velux_command

automation:
  - id: velux_from_knx
    alias: "Velux: commands from KNX"
    mode: queued
    max: 20
    triggers:
      - trigger: knx.telegram
        id: move
        destination: ["24/0/1", "24/0/2"]
        type: "1.008"
        group_value_read: false
        group_value_response: false
        outgoing: false
      - trigger: knx.telegram
        id: stop
        destination: ["24/1/1", "24/1/2"]
        group_value_read: false
        group_value_response: false
        outgoing: false
      - trigger: knx.telegram
        id: position
        destination: ["24/2/1", "24/2/2"]
        type: percent
        group_value_read: false
        group_value_response: false
        outgoing: false
    variables:
      # The last part of the address is the product.
      products:
        "1": { cover: cover.roof_window, script: script.velux_window }
        "2": { cover: cover.roof_window_screen, script: script.velux_screen }
      product: "{{ products[trigger.destination.split('/')[2]] }}"
      command: >-
        {% if trigger.id == 'move' %}{{ 'open' if trigger.value == 'up' else 'close' }}{% else %}{{ trigger.id }}{% endif %}
    actions:
      - action: script.turn_on
        target: { entity_id: "{{ product.script }}" }
        data:
          variables:
            cover: "{{ product.cover }}"
            command: "{{ command }}"
            # KNX counts 0 % as open, Home Assistant 100.
            position: "{{ 100 - trigger.value if trigger.id == 'position' else 0 }}"

  - id: velux_to_knx
    alias: "Velux: position status to KNX"
    mode: queued
    max: 20
    triggers:
      - trigger: state
        entity_id: [cover.roof_window, cover.roof_window_screen]
        attribute: current_position
    variables:
      status: { cover.roof_window: "24/3/1", cover.roof_window_screen: "24/3/2" }
      position: "{{ state_attr(trigger.entity_id, 'current_position') }}"
    conditions:
      # Only a real position. Without one (gateway restart, entity unavailable) nothing is sent.
      - "{{ has_value(trigger.entity_id) and position is number and 0 <= position <= 100 }}"
    actions:
      - action: knx.send
        data:
          address: "{{ status[trigger.entity_id] }}"
          payload: "{{ 100 - position }}"
          type: percent

  - id: velux_screen_up_in_rain
    alias: "Velux: screen up when it starts to rain"
    triggers:
      - trigger: state
        entity_id: binary_sensor.rain
        from: "off"
        to: "on"
    conditions:
      - "{{ has_value('cover.roof_window_screen') and not is_state_attr('cover.roof_window_screen', 'current_position', 100) }}"
    actions:
      - action: cover.open_cover
        target: { entity_id: cover.roof_window_screen }

    What each part does:

    • The scripts run the actual Velux command. The YAML anchor &velux_command gives both scripts the same steps without copying them; each still has its own restart queue.
    • velux_from_knx listens only to writes on the listed addresses, and not to Home Assistant’s own telegrams (outgoing: false). It works out the product and the command, and starts that product’s script.
    • velux_to_knx sends every real position change back, as KNX percent. Buttons with status LEDs and the visualization show the actual position, also when someone used the Velux remote.
    • velux_screen_up_in_rain raises the screen when it starts to rain, unless it is already up. In our house the screens go up in rain; adapt this to your own rule.

    To test it, press a KNX button or write a value from the ETS group monitor, and watch the automation’s trace in Home Assistant. A knx.send from Home Assistant itself is ignored on purpose (outgoing: false).

    Airing with guards

    The same bridge carries a second feature: “airing” from a KNX button or the phone. A window opens, a timer runs, and the window closes again afterwards. Two guards proved necessary:

    • Not in rain. Velux windows with a rain sensor only open a gap while it rains, and the Home Assistant integration reports that sensor: it reads the window’s opening limitation every 5 minutes, so a limitation set by other means also reads as rain. The rain sensor entities are disabled by default; enable them in the entity settings. Airing doesn’t start while either the weather station or a window reports rain.
    • No overlapping runs. A single window, its group and “all windows” can each start an airing. A new one only starts when none of its windows is already in a running one, so one timer never closes a window that another just opened.

    The status LED on the KNX button follows the timer, so you can see from the wall that airing is running.

    What I would check first

    • The gateway’s firmware and connection: the Home Assistant integration needs KLF 200 firmware newer than 2.0.0.0. The setup has to be finished within five minutes of restarting the gateway, while its Wi-Fi access point is still visible, with Home Assistant on your regular network (see the integration docs).
    • The direction of positions: send 25 % from KNX to a screen and check that it moves a quarter of the way down (Home Assistant shows 75), not three quarters.
    • Missing positions: restart the gateway and watch the status addresses in the group monitor. Nothing should be sent until the positions are back.
    • Who answers reads on the status addresses: if a visualization server also answers them, the buttons can show an old position. See which device answers the read.
